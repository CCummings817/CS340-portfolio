# CS-340 Client/Server Development: Grazioso Salvare Dashboard

This repository holds my Project Two work from CS-340: the finished Grazioso Salvare dashboard (ProjectTwoDashboard.ipynb), the CRUD Python module from Project One that powers it (CRUD_Python_Module.py), and the Project Two README (Project_Two_README_Cummings.docx), which documents the project and includes screenshots of the dashboard in action.

**How do you write programs that are maintainable, readable, and adaptable?**

For me it starts with separating the pieces so each one has one job. In Project One I built the CRUD Python module as an AnimalShelter class that handles the MongoDB connection and the create, read, update, and delete operations in one place. I made the constructor take the username, password, host, port, database, and collection as arguments instead of hard-coding them, gave every method input checks and exception handling, and commented the code so someone else could pick it up without needing me to explain it. The real test came in Project Two, when I used that same module to connect the dashboard widgets to the database without changing a single line of it. The dashboard only had to call read() with a query, and the module handled everything else. That made the dashboard code shorter and easier to follow, and when something went wrong I knew which layer to look at. I took the same approach with the dashboard itself by keeping all three rescue profiles in one dictionary, so changing a breed list or an age range means editing one spot instead of hunting through queries.

Because the module is not tied to this one dashboard, it could be reused for any project that stores data in MongoDB. I could point it at a different database and collection just by passing different arguments, and I already see it fitting into an inventory and field data app I have been building for the construction trades, where materials and job records would need the same create, read, update, and delete operations.

**How do you approach a problem as a computer scientist?**

I start with the requirements before I write any code. Coming from about ten years as a business analyst, that part feels natural to me. For this project I read through the Dashboard Specifications Document and the Rescue Type and Preferred Dog Breeds table first and turned each rescue profile into exact query conditions for breed, sex, and age range. Then I built in layers, starting with the database and the CRUD module, then the data table, then the filters, and finally the charts and map, testing each layer before adding the next one. Testing is where I learned the most. When I ran the finished dashboard, I noticed the same dogs showing up more than once and traced it back to the data set having been imported into my collection three times. The queries were right, but the data underneath them was not, and I would not have caught that if I had not checked my results against the original CSV file.

This project was different from my earlier courses because it was a full stack, so I had to think about how the database, the middleware, and the user interface work together instead of just one program. It also had a real client with real requirements, which made me think about the people using it and not just whether the code ran. In the future, I would keep the same approach for other client requests: gather the requirements, design the data model around how the client will actually search the data, check that the data is clean before building on top of it, add indexes for the fields that get queried most, and test every layer against what the client asked for.

**What do computer scientists do, and why does it matter?**

Computer scientists take a problem people are dealing with and build tools that solve it in a way that is reliable and easy to use. That matters because the people who need the tool usually are not developers. Grazioso Salvare trains rescue dogs, and their staff should be spending their time on the dogs, not writing database queries. Before this dashboard, finding a good candidate for water rescue would have meant digging through thousands of shelter records by hand. Now a trainer can click one button and see every dog that fits the profile, where each one is located, and how the breeds break down, all at the same time. That saves time, cuts down on mistakes, and helps them get the right dogs into training faster, which ends up helping the people those dogs will eventually rescue. Since the code is open source and documented, other rescue organizations can adapt it for their own needs too.
